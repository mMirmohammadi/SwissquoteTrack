## Retention format and restore decisions

Source inspected: [live-retention.mjs:161–179](<../../swissquote-wallet/tests/browser/live-retention.mjs#L161-L179>). Credential JSON has exactly `schema`, `devicePassphrase`, `cardWords`, with schema `sepolia-local-recovery-v1`. It does **not** contain a login password or session record. Credential restoration passes only the original device passphrase and card words into a fresh retention run; words never enter the app or an API. No owner seed is decrypted, read, exported, displayed, or transmitted by the harness. Only the ordinary app UI unlocks its encrypted device key.

Snapshot slots contain raw Playwright storage state, including IndexedDB, not wrappers with a schema version, counter, or timestamp. The writer alternates its in-memory slot after each successful positioned write/fsync. There is no documented highest-version field to select. The reader checks both slots, accepts an empty untouched slot, validates every nonempty slot as bounded raw JSON and an encrypted expected-owner/expected-wallet device under the wallet UI origin, then chooses the highest file `mtimeNs`. Conflicting snapshots with equal `mtimeNs` fail closed. Malformed/non-device nonempty slots fail closed rather than guessing. Filesystem time ordering is a conservative local heuristic, not authenticated version metadata; an owner-written replacement or manipulated timestamp is outside its guarantee.

The original path is fixed beneath the exact source-derived `swissquote-wallet/.sepolia-runs/` root. At runtime the root and run directory must be current-UID directories with mode 0700, no symlinks and matching real paths. All original files must be current-UID regular 0600 files with one hardlink. The reader holds `O_NOFOLLOW` handles, checks path/handle device+inode identity repeatedly, and bounds credential JSON to 16 KiB and each raw snapshot to 4 MiB. Size, mtime and ctime must remain stable across each read. It never repairs permissions or edits the original run.

[createLiveRetention:97–125](<../../swissquote-wallet/tests/browser/live-retention.mjs#L97-L125>) creates its run exclusively; calling it with the original run would fail. Resume therefore uses a new UUID run in the same ignored root. It saves the original credentials and a fresh raw restored-context snapshot before any payment and guards the intercepted payment with another snapshot. Cleanup always attempts a fresh bound snapshot before browser close. Original files remain untouched; the new resume run ID is public output, its files remain private. The current helper does not define adding a fresh snapshot to the original run safely, so the fresh resume run is the durable continuation.

## Runtime guards and result contract

Before browser creation and again immediately before the sole payment release, both public nodes must agree on a shared block and expected current owner, threshold one, nonce zero, exactly one USDC, owner/wallet zero ETH, Safe proxy/singleton/fallback/guard pins, protocol dependency code pins, USDC proxy implementation/admin/code pins, exactly the known recovery modules, and no pending module recovery. The strict live service must report an idle, unblocked sender. Unexpected methods, origins, API routes, authentication, funding, deployment, recovery, screening POSTs and API previews are aborted. Only real UI local payment review is used. WebSocket routes are closed; service workers and downloads are disabled. No response is mocked or fulfilled.

The intercepted payment must be a canonical one-USDC ERC-20 transfer to the fixed TREASURY, nonce zero, zero native value, CALL (not delegatecall), zero gas/refund fields, fixed chain/wallet, payment source, and recovered signature of the fixed owner. Unknown request keys, step-up tokens and DeFi fields are rejected. The first-time recipient suffix uses the real UI guard. Payment attempts and released POSTs are counted separately; duplicate requests are never released. No automatic retry exists.

Public JSON schema is `sepolia-payment-resume-v1`. A successful run requires actual transaction hash, full two-node receipt agreement, expected RELAYER sender, Safe `ExecutionSuccess` matching the signed Safe hash with zero payment, no `ExecutionFailure`, exactly one matching USDC Transfer of 1000000 base units, receipt-block nonce one, expected owner unchanged, wallet USDC zero, recipient delta one USDC and owner/wallet ETH zero. Public output never copies arbitrary response strings, browser exception text, auth, storage, passphrase or card words.

HTTP refusal reports only an explicit status allowlist (400/401/403/409/429/502/503, otherwise `unrecognized_status`) and exact recognized 403 sponsorship codes (`SANCTIONS_BLOCK`, `SCREENING_UNAVAILABLE`, `NOT_SPONSORED`, `EFFECTS_MISMATCH`); everything else is `redacted_or_absent_code`. Unknown or pending outcomes instruct public-chain/service inspection without resubmission. A valid transaction hash is recorded before later response validation when available.

The whole runtime has a hard 180-second process deadline; write-stop and fresh-retention cleanup begin at 172 seconds, reserving eight seconds **within** that limit. A stalled cleanup is reported and cannot release a paused payment. Hard process exit may interrupt a stuck cleanup; the previously completed fresh resume snapshot remains the fallback. Portable-tool verification is not repeated because the original run was already verified.
